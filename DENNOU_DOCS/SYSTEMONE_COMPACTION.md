## 1. 背景と課題意識

### 1.1 従来の一括要約（Lossy Summary）の限界

これまでのコンパクション（会話要約）は、一定のトークン数（または章単位）に達した過去ログを**「丸ごと一つの文章に要約する」**方式が主流であった。
しかし、最新の論文 **Context Language Models (CLMs)**（"What If an AI Could Edit Its Own Memory"）でも実証されている通り、この一括要約には致命的な欠点が存在する：

1. **重要な針（Needle）の喪失とハルシネーション**:
   - 過去ログに含まれる重要なファイルパス、ポート番号、設定値、ユーザーとの厳密な約束が、要約によって「〇〇について議論した」という大雑把な記述に丸められたり、誤った数値に歪められたりして失われる。
2. **ノイズの抱え込み**:
   - 失敗したツールの生ログや単なる相槌（ping-pong）、エラー試行錯誤の残骸まで要約の材料に混ぜてしまい、要約文そのものがぼやけてしまう。
3. **生データか要約かの二者択一**:
   - 「全部を生で残す（コンテキスト圧死）」か「全部要約する（情報劣化）」の極端な選択肢しかなく、人間のような「大事な思い出や決定はそのまま鮮明に覚え、細かい雑音だけを忘れる」グラデーションが作れなかった。

### 1.2 解決策：System 1 直感仕分け ＋ 選抜一括要約

本設計では、人間が「直感（System 1）」でノイズをふるい落とし、「熟考（System 2）」で重要な文脈を整理する二重プロセスをコンパクションに導入する：

- **章（コンパートメント）の中の各対話ターン（ユーザー質問・返答・ツール束）を、超高速な判定モデル（TypeSafe Jev）が 1 つずつミリ秒で直感仕分けする**。
- 判定結果は 3 つ：
  - **「維持（Keep）」**: 一字一句正確に残すべき重要な決定・約束。**一切要約せず生データのままプロンプトに復帰**。
  - **「落とす（Drop）」**: モデルのパフォーマンスを下げるだけのノイズ。**プロンプト注入からスキップ（セッション JSONL 実データは 100% 無傷）**。
  - **「要約（Summarize）」**: 細部は不要だが流れとして残すべき情報。**集約して通常 LLM が一括要約**。

## 3. フェーズ 1: System 1 (Jev) の判定仕様

### 3.1 接続エンドポイント ＆ 認証

- **URL**: `https://api.experientiallabs.ai/v1/systemone`
- **認証**: `Authorization: Bearer <EXPERIENTIAL_API_KEY>`（`.env` または Gateway 共通環境変数から解決）
- **キー未設定時**: 自動的にフェイルオープンとなり、System 1 をバイパスして既存の章単位退避（`COMPACTION_FEATURE.md` §7.5 レガシーパス）で動作する。
- **モデル**: `jev-latest`
- **タイムアウト**: 単一リクエストあたり **2,000ms**（超過時は自動フェイルオープン）
- **コスト**: Free Tier 枠内 ($0)

### 3.2 判定単位と原子性の保護（Turn-level 原子性）

単一の回答やツール結果だけが切り離されて文脈喪失するのを防ぐため、判定単位は **ターン単位（ユーザーの質問 ＋ アシスタントの返答 ＋ 関連ツール実行結果の束）** とする：

- `toolCall` と `toolResult` は常に単一ペアとして不可分に扱う。
- 回答が「維持」と判定された場合、そのトリガーとなった直前質問もセットで保持される。

### 3.3 判定プロンプト ＆ Criteria 設計

Jev の `choice` 型クエリを使用し、確率分布（probabilities）付きで 3 択判定を行う。

```json
{
  "model": "jev-latest",
  "state": "【前後の文脈】\n直前: [User] この設定ファイルのポート番号を教えて\n直後: [Assistant] 確認しました。ポート番号は8320です。\n\n【判定対象ターン】\nUser: この設定ファイルのポート番号を教えて\nAssistant: 確認しました。ポート番号は8320です。",
  "questions": {
    "action": {
      "type": "choice",
      "instructions": "常時稼働エージェントのコンテキストの一部です。このターンの扱いを判定してください。",
      "criteria": {
        "維持": "今後大事な決断で正確に覚えるべき重要な決定、設定情報、ユーザーとの約束",
        "要約": "細部は不要だが念のため議論の流れや背景として残す情報",
        "落とす": "ただの動作確認、挨拶、失敗したコマンドの重複など、以後の会話に不要なノイズ"
      }
    }
  }
}
```

### 3.4 レート制限・サーキットブレーカー ＆ フェイルセーフ設計

1. **並列度制限（Concurrency Cap）**:
   - 同時実行数は **デフォルト 8（最大 16 まで設定可能）** に制限し、過剰なバーストを防ぐ。
2. **確信度閾値（Confidence Threshold）**:
   - 判定結果の `confidence >= 0.6` を採用。確率が拮抗している場合（低確信度）は安全側に倒して **「要約」** とする。
3. **包括的サーキットブレーカー（大災害防止）**:
   - 401（認証切れ）、429（レート制限）、5xx エラー、または連続 3 回以上の失敗を検知した場合、即座にサーキットブレーカーを **OPEN** にする。
   - OPEN 状態の間は System 1 を完全スキップし、既存の **`COMPACTION_FEATURE.md` §7.5 のレガシー安全弁パス（章全体の退避 ＆ 章要約目次）へ自動フェイルオープン** する。
   - **自動復旧（HALF_OPEN）**: 60秒のクールダウン経過後、1リクエストのみ試験的に実行（HALF_OPEN）。成功すれば正常復帰（CLOSED）し、失敗すれば再度 60秒 OPEN を維持する。

## 4. フェーズ 2: 選抜一括要約 (Historian) の仕様

### 4.1 要約モデル

- `cli-router/agy-gemini-3.1-flash-lite`（または `gemini-flash-lite`）
- 単発構造化補完（JSON または構造化テキスト出力、セッション非起動・#2032/#2041 遵守）

### 4.2 要約プロンプト設計

Historian には、第1章のタイムスタンプ範囲と、要約対象ターンの生テキスト（truncated）を提示し、一括要約を生成させる。

```text
あなたは常時稼働AIエージェント「Kasou」の記憶整理担当（Historian）です。
以下の対話ターン群は、過去ログの第1章の中で「念のため流れを残す」と判定された部分です。

【第1章の期間】
2026-02-20 10:00 〜 14:00

【要約対象ターン群】
- [User]: SQLiteのWALモードのメリットは何？
  [Assistant]: 読み書きが並行実行できる点です。

【維持される生データ（※参考: これらはそのまま生で残るため、要約に含めないでください）】
- [Assistant]: ポート番号は8320に決定しました。

【指示】
要約対象ターン群の内容を、後から文脈を振り返れる簡潔な要約文（2〜3文）としてまとめてください。
維持される生データの内容を重複して要約する必要はありません。
```

## 5. フェーズ 3: プロンプト復帰とキャッシュ整合性

### 5.1 復帰仕様の拡張（COMPACTION_FEATURE §7.5 拡張）

従来の §7.5 は「章要約目次への全置換」であったが、本設計ではこれを以下のハイブリッド構造へ拡張する：

```text
[システム注記: 過去ログ第1章（2026-02-20）の要約と重要記録]
## 第1章要約
- データベース移行について検討し、WALモードの採用と運用方針を確認した。

## 第1章の重要記録（生データ保持）
[User] この設定ファイルのポート番号を教えて
[Assistant] 確認しました。ポート番号は8320です。

--------------------------------------------------
（※ここから第2章以降の生データが通常通り続く）
```

### 5.2 実削減量の再計算とスライディング連鎖

1. インメモリ合成後、実際のプロンプト総トークン数を再計算する。
2. 「維持」された生ブロックが多いために依然として閾値（950K）を超過している場合は、自動的に **次章（第2章）のスライディング退避へ連鎖** し、確実にコンテキスト上限以下へ収束させる。

### 5.3 Prompt Cache（KV Cache）の保護

- 生成された要約文と維持ブロック群は、静的な章 ID とタイムスタンプ順で決定論的にソート・固定される。
- 圧縮イベント間でプロンプトの接頭辞（Prefix）が固定されるため、高効率な KV キャッシュヒット率を維持する。
