## 1. 背景と課題意識

### 1.1 従来の一括要約（Lossy Summary）の限界

これまでのコンパクション（会話要約）は、一定のトークン数（または章単位）に達した過去ログを**「丸ごと一つの文章に要約する」**方式が主流であった。
しかし、最新の論文 **Context Language Models (CLMs)**（"What If an AI Could Edit Its Own Memory"）でも実証されている通り、この一括要約には致命的な欠点が存在する：

1. **重要な針（Needle）の喪失とハルシネーション**:
   - 過去ログに含まれる重要なファイルパス、ポート番号、設定値、ユーザーとの厳密な約束が、要約によって「〇〇について議論した」という大雑把な記述に丸められたり、誤った数値に歪められたりして失われる。
2. **ノイズの抱え込み**:
   - 失敗したツールの生ログや単なる相槌（ping-pong）、エラー試行錯誤の残骸まで要約の材料に混ぜてしまい、要約文そのものがぼやけてしまう。
3. **生データか要約かの二者択一**:
   - 「全部を生で残す（コンテキスト圧死）」か「全部要約する（情報劣化）」の極端な選択肢しかなく、人間のような「大事な思い出や決定はそのまま鮮明に覚え、細かい雑音だけを忘れる」グラデーションが作れなかった。

### 1.2 解決策：System 1 直感仕分け ＋ 選抜一括要約

本設計では、人間が「直感（System 1）」でノイズをふるい落とし、「熟考（System 2）」で重要な文脈を整理する二重プロセスをコンパクションに導入する：

- **章の中の各ブロック（発言、ツール結果、思考）を、超高速な判定モデル（TypeSafe Jev）が 1 つずつミリ秒で直感仕分けする**。
- 判定結果は 3 つ：
  - **「維持（Keep）」**: 一字一句正確に残すべき重要な決定・約束。**一切要約せず生データのまま残す**。
  - **「落とす（Drop）」**: モデルのパフォーマンスを下げるだけのノイズ。**プロンプトから完全除去**。
  - **「要約（Summarize）」**: 細部は不要だが流れとして残すべき情報。**集約して通常 LLM が一括要約**。

## 3. フェーズ 1: System 1 (Jev) の判定仕様

### 3.1 接続エンドポイント

- **URL**: `https://api.experientiallabs.ai/v1/systemone`
- **認証**: `Authorization: Bearer <xpl_...>`
- **モデル**: `jev-latest`
- **レイテンシ**: 約 150ms 〜 250ms / リクエスト
- **コスト**: Free Tier 枠内 ($0)

### 3.2 判定プロンプト ＆ Criteria 設計

Jev の `choice` 型クエリを使用し、確率分布（probabilities）付きで 3 択判定を行う。

```json
{
  "model": "jev-latest",
  "state": "【前後の文脈】\n直前: [User] この設定ファイルのポート番号を教えて\n直後: [Assistant] 確認しました。ポート番号は8320です。\n\n【判定対象ブロック】\n[Assistant] ポート番号は8320です。",
  "questions": {
    "action": {
      "type": "choice",
      "instructions": "常時稼働エージェントのコンテキストの一部です。このブロックの扱いを判定してください。",
      "criteria": {
        "維持": "今後大事な決断で正確に覚えるべき重要な決定、設定情報、ユーザーとの約束",
        "要約": "細部は不要だが念のため議論の流れや背景として残す情報",
        "落とす": "ただの動作確認、挨拶、失敗したコマンドの重複など、以後の会話に不要なノイズ"
      }
    }
  }
}
```

### 3.3 実測ベンチマーク（実証済み）

| テストケース   | 入力例                                                    | Jev 判定結果 | 確信度 |
| -------------- | --------------------------------------------------------- | ------------ | ------ |
| **重要設定**   | 「ポート番号は8320です」                                  | **維持**     | 96%    |
| **単なる相槌** | 「ping」→「pong」                                         | **落とす**   | 100%   |
| **議論の背景** | 「昨日話したWALモードのメリットやバックアップ設計の検討」 | **要約**     | 88%    |

## 4. フェーズ 2: 選抜一括要約 (Historian) の仕様

### 4.1 要約モデル

- `cli-router/agy-gemini-3.1-flash-lite`（または指定の軽量・高速要約モデル）
- 単発補完（JSON または構造化テキスト出力）

### 4.2 要約プロンプト設計

ブロック単体をバラバラに要約すると文脈が壊れるため、**第1章全体の文脈を見せながら、「要約」に選ばれたブロック群だけを一括要約**する。

```text
あなたは常時稼働AIエージェント「Kasou」の記憶整理担当（Historian）です。
以下の会話ブロック群は、過去ログの第1章の中で「念のため流れを残す」と判定された部分です。

【第1章の全体概要】
期間: 2026-02-20 10:00 〜 14:00
主要トピック: データベース移行とアーキテクチャ議論

【要約対象ブロック群】
- ブロック #1: SQLiteのWALモードのメリットに関する検討
- ブロック #2: チェックポイント運用の注意点についての議論

【維持される生ブロック（※参考: これらはそのまま残るため、要約に含める必要はありません）】
- 「ポート番号は8320に決定」

【指示】
要約対象ブロック群の内容を、後から文脈を振り返れる簡潔な要約文（2〜3文）としてまとめてください。
維持される生ブロックの内容を重複して書く必要はありません。
```

## 5. フェーズ 3: プロンプト復帰とキャッシュ整合性

### 5.1 インメモリ合成構造

コンパクション完了後、モデルに渡るプロンプト先頭は以下の構造に再構成される：

```text
[システム注記: 過去ログ第1章（2026-02-20）の要約と重要記録]
## 第1章要約
- データベース移行について検討し、WALモードの採用と運用方針を確認した。

## 第1章の重要記録（生データ保持）
[Assistant] ポート番号は8320です。

--------------------------------------------------
（※ここから第2章以降の生データが通常通り続く）
```

### 5.2 Prompt Cache（KV Cache）の保護

- 生成された要約文と維持ブロック群は、静的な章 ID とタイムスタンプ順で決定論的にソートされる。
- 毎ターン動的に変わる文字列（残りトークン数や現在時刻など）は含めず、一度作成された章要約は次回以降 100% キャッシュヒット（Cache Read 99%）するように固定される。
